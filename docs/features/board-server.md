# 機能設計：ボードのサーバー

M2 で作る Go のサーバーの設計です。ボードは1つで、付箋はメモリに持ちます。画面とやり取りするメッセージの形は [interfaces/messages.md](../interfaces/messages.md)、画面の側の処理は [features/board-sync.md](board-sync.md) にあります。

## 全体の分け方

サーバーのコードは `server/` に置き、1つの Go のモジュールにします（モジュールのパスは `github.com/och-kazuki/realtime-board/server`）。Go は実装を始める時点の最新の安定版を使います。

| パッケージ | 役割 | 動かす goroutine |
|---|---|---|
| `cmd/board-server` | 設定を読み、Hub と HTTP のサーバーを動かし、止める | main |
| `internal/board` | 付箋の一覧を持ち、操作を確かめて反映する | なし（呼び出した goroutine で動く） |
| `internal/protocol` | メッセージの形と、JSON との変換 | なし |
| `internal/hub` | ボードの状態と接続の一覧を持ち、操作を1つずつ処理して全員に配る | Hub が1つ |
| `internal/transport` | WebSocket の接続を受け付け、メッセージを読み書きする | 接続ごとに2つ |

`board` には goroutine も通信の処理も入れません。画面の付箋の状態の関数と同じく、入力だけで結果が決まるので、通信なしでテストできます（ADR-009 と同じ考え方）。

```
ブラウザ ──WebSocket── transport ──channel── hub ──関数の呼び出し── board
                       （接続ごとに           （1つ）
                         読み取りと書き込み）
```

## ボードの状態（`board`）

付箋の一覧を重なりの順番に並べた slice で持ちます。一覧の変え方は画面と同じ決まり（[interfaces/messages.md](../interfaces/messages.md) の「画面とサーバーで同じに当てる決まり」）に従います。

| 関数 | すること |
|---|---|
| 操作を反映する | 操作を受け取り、決まりに合えば一覧を変えて、配るメッセージのもとになる結果を返す。合わなければ一覧を変えずにエラーを返す |
| 一覧を写して返す | スナップショットに使う。呼び出した側が書き換えても一覧が変わらないように、写しを返す |

操作は次の順に確かめます。最初に合わなかったところでエラーを返します（ADR-017）。

| 操作 | 確かめること | 合わないときのエラー |
|---|---|---|
| 追加 | `id` が UUID の形か | `invalid` |
| 追加 | `x` と `y` が整数で、ボードの範囲の中か | `invalid` |
| 追加 | 同じ `id` の付箋がないか | `already_exists` |
| 移動 | `x` と `y` が整数で、ボードの範囲の中か | `invalid` |
| 移動、文字の変更、削除 | その `id` の付箋があるか | `not_found` |
| 文字の変更 | 文字が200字以下か（`utf8.RuneCountInString` で数える。ADR-013） | `invalid` |

位置は JSON の数を `float64` で読み、整数かどうかと範囲を `board` で確かめます。`int` で読むと、`10.5` のような値で JSON の読み取りそのものが失敗し、「形の壊れたメッセージ」として接続を切ることになるためです。整数でない位置は、取り決めでは `invalid` を返すと決めています。

付箋の数は多くても数百枚と見込み、`id` で付箋を探すときは一覧を頭から順に見ます。

## Hub（`hub`）

ボードの状態（`board`）と、接続している画面の一覧は、Hub の goroutine だけが読み書きします。ほかの goroutine は channel で Hub に頼むだけです。状態を読み書きする goroutine が1つだけなので、mutex を使わずにデータ競合を防げます。また、Hub は操作を1つずつ処理するので、操作の順番はサーバーが決めることになります。

Hub は次の3つの channel を受け取ります。

| channel | 送る goroutine | 中身 |
|---|---|---|
| 登録 | 接続を受け付けた goroutine | 新しい接続 |
| 登録の取り消し | 接続の読み取りの goroutine | 終わった接続 |
| 操作 | 接続の読み取りの goroutine | 接続と、その接続から届いた操作 |

接続ごとに、その接続へ送るメッセージを入れる channel（送信待ち）を持ちます。送信待ちには32個までためられます。Hub はメッセージを JSON にしてから送信待ちに入れるので、全員に配るときも JSON にするのは1回だけです。

| 届いたもの | Hub がすること |
|---|---|
| 登録 | 接続の一覧に加え、その接続の送信待ちに `snapshot` を入れる。そのあと全員に `presence` を配る |
| 登録の取り消し | その接続が一覧にあれば、一覧から除き、送信待ちの channel を閉じる。そのあと全員に `presence` を配る。一覧になければ何もしない（すでに切り離した接続） |
| 操作 | 送った接続が一覧になければ何もしない。あれば `board` で反映し、受け付けたら全員に結果を配る。受け付けなかったら、送った接続にだけ `error` を入れる |
| 止める合図（`context` の取り消し） | すべての接続を一覧から除いて送信待ちの channel を閉じ、終わる |

### Hub は待たない

Hub は送信待ちに入れるとき、空きがなければ待たずに、その接続を切り離します（一覧から除き、送信待ちの channel を閉じる）。1つの遅い接続のために Hub が止まると、ほかの全員への配信も止まるためです（M2-AC-12）。切り離したあとは全員に `presence` を配ります。

`snapshot` と `error` を入れるときも同じで、Hub は送信待ちの空きを待ちません。Hub がネットワークや、ほかの goroutine を待つことはありません。

`snapshot` は、登録したときにその接続の送信待ちへ入れます。そのあとに配る結果も同じ送信待ちに入るので、`snapshot` と結果の間で取りこぼしは起きません。

### 送信待ちの channel を閉じるのは Hub だけ

送信待ちの channel を閉じるのは Hub だけで、閉じる前に必ず一覧から除きます。一覧にある接続にだけ送るので、閉じた channel に送ることはありません。切り離したあとに同じ接続から登録の取り消しが届いても、一覧にないので2回閉じることもありません。

## 接続（`transport`）

`/ws` へのリクエストを受け付け、WebSocket の接続にします。WebSocket のライブラリには [coder/websocket](https://github.com/coder/websocket) を使います。`context` に対応していて、複数の goroutine から同じ接続に書き込んでも安全なためです。

### 受け付けるとき

- 接続元（`Origin`）を確かめ、許可したサイトのページからの接続だけを受け付ける。許可するサイトは起動時の設定で渡す（開発では `localhost:5173` と `127.0.0.1:5173`）。ライブラリの `AcceptOptions` の `OriginPatterns` に渡し、`InsecureSkipVerify` は使わない
- 1つのメッセージの大きさの上限を 4096 バイトにする（ライブラリの `SetReadLimit`）。超えるとライブラリがコード 1009 で接続を閉じる

ブラウザは WebSocket でつなぐときに必ず `Origin` を付けます。そのため、ブラウザで開いたほかのサイトのページからの接続は、この確認で断れます。`Origin` を付けないリクエスト（ブラウザ以外のプログラムからの接続）をライブラリがどう扱うかは、実装のときにライブラリのコードで確かめ、この設計書に書き足します。

Vite の開発サーバーは中継する前に WebSocket の接続元を確かめません（[Vite の説明](https://vite.dev/config/server-options)）。接続元を確かめるのはサーバーの役割です。Vite の中継の設定では `rewriteWsOrigin` を使いません。使うと、`Origin` が中継先に合わせて書き換えられ、サーバーで接続元を確かめられなくなるためです。

### 接続ごとの goroutine

1つの接続につき、次の2つの goroutine を動かします。

| goroutine | すること | 終わるとき |
|---|---|---|
| 読み取り（リクエストを受け付けた goroutine がそのまま担う） | メッセージを読み、`protocol` で操作に変えて Hub に送る | 読み取りでエラーが起きたとき（相手が閉じた、書き込みの goroutine が閉じた、大きすぎるメッセージ）と、形の壊れたメッセージが届いたとき |
| 書き込み | 送信待ちからメッセージを取り出し、ブラウザへ書き込む。1回の書き込みは5秒で打ち切る | 送信待ちの channel が閉じられたとき、書き込みに失敗したとき、読み取りの goroutine が終わったとき |

読み取りの goroutine は終わるときに次の順で後始末をします。

1. Hub に登録の取り消しを送る
2. 書き込みの goroutine に終わる合図を出し（`context` の取り消し）、終わるのを待つ
3. 接続を閉じる

書き込みの goroutine は、送信待ちの channel が閉じられたら、コード 1013 で接続を閉じて終わります。接続が閉じると読み取りでエラーが起きるので、読み取りの goroutine も終わります。どちらから終わり始めても、2つの goroutine はどちらも終わります（M2-AC-13）。

読み取りの goroutine が Hub に送るとき（登録、操作、登録の取り消し）は、Hub が止まっていないかも同時に見ます（`select` で Hub が終わった合図も待つ）。サーバーを止めたあとに、誰も受け取らない channel へ送ろうとして止まったままにならないようにするためです。

ブラウザへの書き込みは、書き込みの goroutine だけがします。読み取りの goroutine と Hub は接続に書き込みません。

### 生存確認（ping）は M2 では送らない

一定の間隔で ping を送り、応答のない接続を切る仕組みは M2 では作りません。M2 ではボードを localhost で開くので、タブやブラウザを閉じると接続も閉じ、相手がいないのに接続だけが残ることがほとんどないためです。

また、coder/websocket の `Ping` は ping を送ってから応答が届くまで待ちます。書き込みの goroutine で `Ping` を呼ぶと、待っている間は送信待ちからメッセージを取り出せません。ping を入れるときは、ping のための goroutine を別に動かします。インターネットに公開する M4 で、つなぎ直す仕組み（M3）と合わせて入れることを考えます。

## 起動と停止（`cmd/board-server`）

| 設定 | 初期値 | 内容 |
|---|---|---|
| `-addr` | `127.0.0.1:8080` | 待ち受けるアドレス。ほかのパソコンからつなげないように、`127.0.0.1` で待ち受ける |
| `-allowed-origins` | `localhost:5173,127.0.0.1:5173` | 接続を許可するサイト（`Origin` のホストとポート） |

起動すると、Hub の goroutine を動かしてから HTTP のサーバーで待ち受けます。Ctrl+C（SIGINT）か SIGTERM を受け取ったら、`context` を取り消して Hub を止めます。Hub はすべての送信待ちの channel を閉じるので、接続ごとの goroutine もすべて終わります。

接続したときと切れたときに、そのときの接続の数を `log/slog` でログに出します。送信待ちがあふれて切り離したときも、ログに出します。

## 開発のときの動かし方

- サーバーは `server/` で `go run ./cmd/board-server` で動かす
- 画面は `web/` で `npm run dev` で動かし、`http://localhost:5173` を開く
- Vite の開発サーバーの設定（`vite.config.ts` の `server.proxy`）で、`/ws` を `http://127.0.0.1:8080` へ中継し、`ws: true` を付ける

起動とテストの手順は、実装のときに `server/` と `web/` の README に書きます（M2 の要件）。

## テスト

| 対象 | 方法 |
|---|---|
| `board` | 操作ごとに、受け付ける値と受け付けない値を表にしたテスト。並び順は、画面と同じ例（`docs/interfaces/note-operations.json`）で確かめる |
| `protocol` | 形の壊れたメッセージ（JSON でない、知らない `type`、項目が足りない、型が違う）を見分けられるか |
| `hub` | ネットワークを使わず、送信待ちの channel を直接読む偽の接続で確かめる。全員に同じ順番で配られるか、`error` が送った本人にだけ届くか、`presence` の数、送信待ちを読まない接続が切り離されてもほかの接続に配られ続けるか |
| `transport` | `httptest` で立てたサーバーに、coder/websocket の `Dial` で実際につなぐ。ほかのサイトの `Origin` での接続が断られるか、大きすぎるメッセージと形の壊れたメッセージで接続が閉じられるか、2つの接続の間で操作が配られるか |
| goroutine の後始末 | 接続を閉じたあと、goroutine の数（`runtime.NumGoroutine`）が接続する前の数に戻るか。すぐには戻らないので、少し待ちながら確かめる |
| データ競合 | すべてのテストを `go test -race ./...` で実行する |

## AI のコードを読むときに確かめること

M2 のコードは AI が書きます。サーバーのコードを読むときは、次の点を確かめます。

- Hub と接続ごとの goroutine が、接続が切れたあと、またはサーバーを止めたあとに、すべて終わるか
- Hub が送信待ちに入れるところ（`snapshot`、`error`、結果、`presence`）が、すべて待たない形（`select` の `default`）になっているか
- 送信待ちの channel を閉じるのが Hub だけで、閉じる前に一覧から除いているか
- 読み取りの goroutine が Hub に送るところで、Hub が終わった合図も待っているか
- 1つの接続に、複数の goroutine から書き込んでいないか
- `board` と接続の一覧を、Hub の goroutine のほかから読み書きしていないか
- 接続元の確認が有効か（`InsecureSkipVerify` を使っていないか）
- 位置と文字の決まりが、取り決めと画面の付箋の状態の関数と同じか

## 設計で決めたこと

| 決めたこと | 理由 |
|---|---|
| ボードの状態と接続の一覧は、Hub の goroutine だけが読み書きする（ADR-019） | mutex を使わずにデータ競合を防げ、操作の順番もサーバーで1つに決まる。goroutine と channel の使い方を学ぶ題材にもなる |
| WebSocket のライブラリに coder/websocket を使う（ADR-018） | `context` に対応し、`Origin` の確認と、メッセージの大きさの上限を設定だけで入れられる。gorilla/websocket は解説が多いが、1つの接続へ書き込めるのは1つの goroutine だけという決まりを自分で守る必要がある |
| 接続した直後に、WebSocket でボードの中身（`snapshot`）を送る（ADR-020） | REST で取ってから WebSocket でつなぐと、取ってからつなぐまでの間の操作を取りこぼす。Hub が登録と同時に送信待ちへ入れれば、取りこぼしが起きない |
| 送信待ちがあふれた接続は切り離す | Hub が1つの遅い接続を待つと、ほかの全員への配信も止まる。切り離された画面は接続が切れたと表示する |
| 形の壊れたメッセージでは `error` を返さずに接続を切る | 正しく作った画面からは届かないため。値が決まりに合わないだけのメッセージには `error` を返し、画面が送った操作の結果を待ち続けないようにする |
| ping は M2 では送らない | localhost では、接続だけが残ることがほとんどない。`Ping` は応答を待つので、入れるときは専用の goroutine が要る |
| サーバーは `127.0.0.1` で待ち受ける | M2 ではほかのパソコンから開かない（M2 の要件） |
