# 機能設計：サーバーとの同期（画面）

画面の側で、サーバーとつなぎ、付箋の操作を送り、届いたメッセージで画面を更新する部分の設計です。メッセージの形は [interfaces/messages.md](../interfaces/messages.md)、サーバーの側は [features/board-server.md](board-server.md)、付箋の状態の関数は [features/notes.md](notes.md) にあります。

## 役割の分け方

| 部分 | 役割 |
|---|---|
| 接続 | WebSocket を開き、メッセージを JSON にして送る。届いたメッセージを JSON から読んで渡す。付箋の操作の中身は扱わない |
| 同期の状態の関数 | サーバーが確定した付箋の一覧、確定を待っている自分の操作、接続の状態、開いている画面の数を持ち、届いたメッセージで更新する。通信の処理を入れない |
| ボードのフック | 4つの関数で操作をメッセージにして送り、届いたメッセージを同期の状態の関数に渡す。画面に表示する付箋の一覧を作る |
| 付箋の状態の関数 | M1 のまま使い、スナップショットで一覧を置き換える操作を足す |

通信の処理が入るのは、接続とボードのフックだけです。同期の状態の関数と付箋の状態の関数は、入力だけで結果が決まるので、通信なしでテストできます（ADR-009）。

## 接続

- `main.tsx` で、React で画面を描く前に1つだけ作り、`App` に渡す
- つなぐ先はページと同じホストの `/ws` にする。ページを `https:` で開いたときは `wss:`、それ以外は `ws:` を使う
- 接続の状態は `connecting`（開いている途中）、`open`、`closed` の3つ
- 送るのは `open` の間だけにする。それ以外のときは送らずに捨てる
- 届いたメッセージは JSON として読み、`type` が取り決めにあるものだけを渡す。JSON として読めないものと、知らない `type` のものは、捨てて開発者ツールのコンソールに出す
- 閉じたら `closed` にし、購読している側に知らせる。つなぎ直さない（M2 の要件）
- WebSocket を作る関数を受け取れるようにし、接続のテストでは偽の WebSocket を渡す

接続を React の外で作るのは、開発のときの React の StrictMode が effect を2回動かすためです。effect の中で接続を作ると、開発中は接続が2回でき、開いている画面の数が一瞬増えて見えます。

### 購読する側がいない間に届いたもの

接続は、購読する側がいない間に届いたメッセージと、閉じたという知らせをためておき、購読が始まったら届いた順に渡します。

接続を React の外で作るので、ボードのフックが購読を始める前に WebSocket が開き、`snapshot` が届くことがあります。localhost ではつながるまでが速いので、起こりやすくなります。ためておかないと `snapshot` を取りこぼし、画面がずっと「接続しています」のままになります。

## 同期の状態

同期の状態の関数が持つものは次のとおりです。

| 項目 | 内容 |
|---|---|
| 確定した一覧 | サーバーから届いた `snapshot` と結果（`note.created` など）だけを反映した付箋の一覧 |
| 確定待ちの操作 | 送ったが、まだ結果も `error` も届いていない自分の操作。送った順に並べ、それぞれ `requestId` を持つ |
| 接続の状態 | `connecting`（`snapshot` が届くまで）、`connected`、`disconnected` の3つ |
| 開いている画面の数 | `presence` で届いた数。まだ届いていなければ、数がないことを表す値 |

接続の状態は、WebSocket が開いたときではなく、`snapshot` が届いたときに `connected` にします。`snapshot` が届くまでは付箋の一覧がなく、操作しても反映する先がないためです。

| 出来事 | 変わること |
|---|---|
| 操作を送った | 確定待ちの最後に加える |
| `snapshot` が届いた | 確定した一覧を置き換え、接続の状態を `connected` にする |
| 結果（`note.created`、`note.moved`、`note.textUpdated`、`note.deleted`）が届いた | 付箋の状態の関数で、確定した一覧に反映する。`requestId` が確定待ちにあれば、その操作を確定待ちから除く |
| `error` が届いた | `requestId` の操作を確定待ちから除く |
| `presence` が届いた | 開いている画面の数を変える |
| 接続が閉じた | 接続の状態を `disconnected` にし、確定待ちを空にする |

### 画面に表示する一覧

画面に表示する付箋の一覧は、確定した一覧に、確定待ちの操作を送った順に付箋の状態の関数で反映し直したものです。この形には次の利点があります。

- 自分の操作はサーバーの結果を待たずに表示に出る。追加した付箋にすぐ文字を入力でき、手を離した位置に付箋が残る（M1 と同じ使い心地）
- サーバーが受け付けなかった操作は、確定待ちから除かれ、表示から消える
- 確定した一覧は、サーバーが配った順番どおりに操作を反映して作るので、ほかの人の操作と入れ違っても、最後にはどの画面もサーバーと同じになる（M2-AC-06）

たとえば、A さんが付箋 P を動かし、ほぼ同時に B さんが P の文字を変えて、サーバーには B さんの操作が先に届いたとします。

- A さんの画面：動かした直後は、移動が確定待ちにあり、P は動かした位置に表示される。B さんの文字の変更の結果が届くと、確定した一覧に反映され、その上に確定待ちの移動を反映し直すので、P は B さんの文字で、A さんが動かした位置に表示される。続いて A さんの移動の結果が届くと、確定した一覧に反映され、確定待ちから除かれる
- B さんの画面：文字の変更の結果、A さんの移動の結果の順に届き、確定した一覧に反映される

どちらの画面でも、確定した一覧にはサーバーと同じ順番で2つの操作が反映されます。

ほかの人が消した付箋への自分の操作は、反映し直しても付箋の状態の関数が何も変えません（一覧にない `id` への操作は何も変えない）。そのあとサーバーから `not_found` の `error` が届き、確定待ちから除かれます。

## ボードのフック

`useBoard(connection)` は接続を受け取り、次のものを画面の部品に渡します。

| 渡すもの | 内容 |
|---|---|
| 付箋の一覧 | 画面に表示する一覧 |
| 接続の状態 | `connecting`、`connected`、`disconnected` |
| 開いている画面の数 | 数か、まだ届いていないことを表す値 |
| 追加、移動、文字の変更、削除の4つの関数 | 下の表のとおり |

4つの関数は、接続の状態が `connected` でないときは何もしません（追加の関数は `id` の代わりに `null` を返します）。`connected` のときは、送る前に次のことを確かめ、送るときは操作ごとに `requestId` を UUID で作って、確定待ちに加えます。

| 関数 | 何もしないとき | 送るメッセージ |
|---|---|---|
| 追加 | 位置が数でないとき | `note.create`。位置は整数にしてボードの範囲に収めてから送る。`id` は UUID で作り、作った `id` を返す |
| 移動 | 表示中の一覧にない `id`、数でない位置、範囲に収めたあとの位置が今と同じとき | `note.move` |
| 文字の変更 | 表示中の一覧にない `id`、今と同じ文字、200字を超える文字のとき | `note.updateText` |
| 削除 | 表示中の一覧にない `id` のとき | `note.delete` |

M1 では、追加の位置を整数にして範囲に収めるのは付箋の状態の関数でした。サーバーは範囲の外の位置を収めずに受け付けないので（ADR-017）、M2 では送る前にボードのフックで収めます。

同じ値かどうかは画面に表示している一覧と比べます。利用者が見ている付箋と比べるためです。

ボードのフックは effect の中で接続を購読し、届いたものを同期の状態の関数に渡します。effect の後始末で購読をやめます。

UUID は M1 と同じく `crypto.randomUUID()` で作ります。M2 ではボードを localhost で開くので使えます。

## 画面の部品への影響

`App` は接続を受け取って `useBoard()` に渡し、開いている画面の数と接続の状態を表示します。接続していない間の表示と操作は [screens/board.md](../screens/board.md) にあります。`App` のほかの画面の部品（`BoardSurface`、`StickyNote`、`NoteEditor`、ドラッグのフック）は変えません。

## テスト

| 対象 | 方法 |
|---|---|
| 同期の状態の関数 | 出来事の並びを渡し、確定した一覧、確定待ちの操作、表示する一覧を確かめる。ほかの画面の操作と自分の操作が入れ違う場合（上の例）、受け付けられなかった場合、接続が閉じた場合を含む |
| 付箋の状態の関数 | M1 のテストに、一覧の置き換えのテストと、取り決めの例（`docs/interfaces/note-operations.json`）を使うテストを足す |
| 接続 | 偽の WebSocket を渡し、購読の前に届いたメッセージが購読したときに届いた順に渡されるか、`open` でないときに送らないか、読めないメッセージを捨てるか |
| ボードのフック | 偽の接続を渡す。描く前に `snapshot` が届いていても表示されるか、4つの関数が送るメッセージ、接続していない間は送らないか |
| 画面の部品 | 準備で偽の接続を渡し、空の `snapshot` を届けてから、M1 と同じことを確かめる。確かめる内容は変えない（M2-AC-15）。M2 で足した表示のテストも書く |

## 受け入れ条件の確かめ方

サーバーのテストの方法は [features/board-server.md](board-server.md) の「テスト」にあります。

| ID | 確かめる場所 |
|---|---|
| M2-AC-01 | サーバーの `transport` のテスト（あとからつないだ接続に、それまでの付箋が並び順どおりに `snapshot` で届く）と、ボードのフックのテスト（`snapshot` の一覧がそのまま表示される） |
| M2-AC-02 | サーバーの `hub` と `transport` のテスト（追加の結果が全員に届く）と、ボードのフックのテスト（届いた `note.created` が表示に出る） |
| M2-AC-03 | サーバーの `hub` と `transport` のテストと、ボードのフックのテスト（届いた `note.moved` で付箋が移り、一覧の最後に来る） |
| M2-AC-04 | サーバーの `hub` と `transport` のテストと、画面の部品のテスト（編集中と、取り消したときは何も送らない） |
| M2-AC-05 | サーバーの `hub` と `transport` のテストと、ボードのフックのテスト（届いた `note.deleted` でその付箋だけが消える） |
| M2-AC-06 | サーバーの `hub` のテスト（複数の接続から送った操作が、全員に同じ順番で届く）、同期の状態の関数のテスト（入れ違いの例）、画面とサーバーの両方の取り決めの例のテスト |
| M2-AC-07 | 画面の部品のテスト（編集中の付箋とドラッグ中の付箋に `note.deleted` が届くと、付箋が消え、編集やドラッグが終わる） |
| M2-AC-08 | サーバーの `hub` のテスト（`presence` の数）と、画面の部品のテスト（届いた数が表示される） |
| M2-AC-09 | 画面の部品のテスト（`snapshot` が届くまでと閉じたあとに、そのことが表示され、「付箋を追加」が押せず、編集が終わる）と、ボードのフックのテスト（送らない） |
| M2-AC-10 | サーバーの `board` と `protocol` のテストと、`transport` のテスト（受け付けなかった操作がほかの接続に届かない） |
| M2-AC-11 | サーバーの `transport` のテスト |
| M2-AC-12 | サーバーの `hub` のテスト |
| M2-AC-13 | サーバーの goroutine の後始末のテスト |
| M2-AC-14 | サーバーのテストを `go test -race ./...` で実行する |
| M2-AC-15 | M1 の自動テスト（準備だけを変える）と、M1 の手動の確認の項目 |
| M2-AC-16 | 手動。Chrome、Edge、Firefox のうち2つを開いて確かめる |
| M2-AC-17 | 設計とコードのレビュー（画面の部品は接続を `useBoard()` に渡すだけで、メッセージを作ったり読んだりしていないか） |

M2-AC-17 の「付箋の操作をサーバーに送る処理がボードのフックの中にだけある」は、次のように満たします。付箋の操作をメッセージにするのはボードのフックだけで、接続はフックが作ったメッセージを JSON にして運ぶだけです。接続は付箋の操作の中身を扱いません。

## 設計で決めたこと

| 決めたこと | 理由 |
|---|---|
| 自分の操作は、サーバーの結果を待たずに表示に出す。確定した一覧と確定待ちの操作に分けて持ち、表示はその2つから作る（ADR-021） | 追加した付箋にすぐ文字を入力でき、手を離した位置に付箋が残る。確定した一覧はサーバーの順番だけで作るので、入れ違っても最後にはサーバーと同じになる。最初の設計メモでは、まずサーバーの結果を待ってから表示する作り方にし、慣れてから変えるとしていた。しかし待つ作り方では、結果が届くまで追加した付箋が一覧になく、すぐに編集を始める流れを保つための処理が別に要る |
| 接続は React の外で1つだけ作り、`App` に渡す | 開発中に StrictMode で接続が2回できないようにするため。テストでは偽の接続を渡せる |
| 購読する側がいない間に届いたものをためておく | フックが購読を始める前に届いた `snapshot` を取りこぼさないため |
| 接続の状態は、`snapshot` が届いたときに `connected` にする | `snapshot` が届くまでは付箋の一覧がないため |
| 接続が閉じたら、確定待ちの操作を捨てる | つなぎ直さないので結果が届かず、受け付けられたか分からない操作を表示に残さないため |
| 追加の位置は、送る前にボードのフックで範囲に収める | サーバーは範囲の外の位置を受け付けないため（ADR-017） |
