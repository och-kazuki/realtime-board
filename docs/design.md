# リアルタイム共有ボード 設計メモ

複数人が同じボードに付箋を貼り、ほかの人の操作がすぐに画面へ反映されるアプリを、TypeScript（画面）と Go（サーバー）で作るための設計メモです。学習の題材として、Go の並行処理、同時に編集したときの扱い、リアルタイム通信を中心に学ぶことを目的にしています。

---

## 1. 作るもの

### 最初のバージョンで作る機能

- ボードを作り、URL で共有して開く
- 付箋の追加・移動・文字の編集・削除
- ほかの人の操作がすぐに自分の画面にも反映される
- いまボードを開いている人数の表示

### あとで足す機能

- ログインと、ボードのメンバー・権限（閲覧だけ／編集できる）
- 操作の履歴と「元に戻す」
- 付箋の色・大きさの変更、ほかの人のカーソルの表示

### 作らない機能

- 1つの付箋の文字を、複数人で同時に1文字ずつ編集する機能（共同エディタのような機能）。CRDT などの専門的な仕組みが必要になり、最初の題材としては重すぎるためです。このアプリでは付箋1枚を単位に編集を扱います。

---

## 2. 全体の構成

```
ブラウザ（React + TypeScript）
    │  WebSocket（操作と通知）
    ▼
Go サーバー（ボードごとに1つの goroutine）
    │
    ▼
PostgreSQL（ボードと付箋を保存）
```

- ボードの一覧と作成は、ふつうの HTTP の API（REST）で行います。
- ボードを開くと WebSocket でつなぎ、接続した直後にサーバーがボードの中身をまとめて送ります（スナップショット）。
- そのあとの操作と通知は、すべて WebSocket で送り合います。

---

## 3. サーバー側（Go）の設計

### 3.1 ボードごとに1つの goroutine が状態を持つ

ボードごとに goroutine を1つ動かし（以下 Hub と呼びます）、そのボードの状態（付箋の一覧と、接続中の利用者）は Hub だけが読み書きします。ほかの goroutine は channel で Hub に操作を送るだけです。

- Hub は届いた操作を1つずつ順番に処理するので、操作の順番はサーバーが決めることになります。
- 状態を読み書きする goroutine が1つだけなので、mutex を使わずにデータ競合を防げます。Go の「通信によってメモリを共有する」という考え方をそのまま使う設計です。

### 3.2 接続ごとに2つの goroutine

ブラウザとの接続1つにつき、次の2つの goroutine を動かします。

- 読み取り用：ブラウザから届いたメッセージを読み、検証してから Hub に送ります。
- 書き込み用：Hub からの送信待ちのメッセージ（バッファ付きの channel）を読み、ブラウザへ送ります。

送信待ちの channel があふれた接続（通信が遅い、止まっているなど）は切断します。1人の遅い接続のために、ほかの全員を待たせないためです。切断されたブラウザは再接続し、スナップショットを受け取り直します。

また、一定の間隔で生存確認（ping）を送り、応答がない接続を切断します。

### 3.3 Hub の起動と終了

- そのボードへの最初の接続で Hub を起動します。
- 全員が抜けてから一定時間がたったら、Hub を終了します。終了しないと、使われないボードの goroutine が残り続けます。
- ボード ID から Hub を探す一覧（map）は、複数の接続から同時に使われるので、ここだけは mutex で守ります。
- Hub を終了するときは、この mutex を持ったまま一覧から自分を消してから終了します。順番を守らないと、終了しかけの Hub を見つけた新しい接続が、誰も受け取らない channel に送ろうとして止まったままになります。

### 3.4 使うライブラリ

WebSocket は Go の標準ライブラリには含まれていないので、ライブラリを使います。

| 候補 | 特徴 |
|---|---|
| [coder/websocket](https://github.com/coder/websocket)（迷ったらこれ） | `context` に対応している。複数の goroutine から同じ接続に書き込んでも安全 |
| [gorilla/websocket](https://github.com/gorilla/websocket) | 古くから広く使われていて、解説や例が多い |

接続を受け付けるときは、接続元のサイト（Origin）を確認し、自分の画面以外からの接続を拒否します。coder/websocket では `AcceptOptions` の `OriginPatterns` で許可するサイトを指定します。`InsecureSkipVerify` で確認を無効にするのは、手元での確認に限ります。

## 4. 通信の約束（メッセージの形）

メッセージは JSON で、`type` で種類を分けます。TypeScript では判別可能なユニオン型、Go では `type` を読んでから中身を解釈する形で扱います。

### ブラウザからサーバーへ

| type | 中身 | 意味 |
|---|---|---|
| `note.create` | `requestId`、`x`、`y`、`text` | 付箋を追加する |
| `note.move` | `requestId`、`noteId`、`x`、`y` | 付箋を動かす |
| `note.update` | `requestId`、`noteId`、`text`、`version` | 付箋の文字を変える |
| `note.delete` | `requestId`、`noteId`、`version` | 付箋を消す |

### サーバーからブラウザへ

| type | 中身 | 送る相手 |
|---|---|---|
| `snapshot` | `seq`、付箋の一覧 | 接続した本人（接続した直後） |
| `note.created`、`note.moved`、`note.updated`、`note.deleted` | `seq`、変わった付箋、元になった操作の `requestId` | ボードを開いている全員 |
| `presence` | 接続している人数 | ボードを開いている全員 |
| `error` | `requestId`、エラーの種類、説明 | 操作を送った本人 |

- `requestId` は、ブラウザが自分の送った操作の結果を見分けるための番号です。成功したときの通知にも、元になった操作の `requestId` を付けて全員に配ります。操作した本人は、この番号で自分の操作が成功したことを知ります。
- スナップショットは接続した直後にだけ送ります。取り直したいときは、いったん切断して再接続します。
- Hub は新しい接続を登録するときに、その接続の送信待ちの channel にスナップショットを入れます。そのあとの通知も同じ channel に入るので、スナップショットと通知の間で取りこぼしは起きません。
- `seq` はボードごとの通し番号です。この設計では遅い接続を切断するので、1つの接続の中で通知が抜けることはありません。`seq` は、再接続したときに手元の状態とスナップショットのどちらが新しいかを確かめたり、テストで通知の順番を確かめたりするために使います。

TypeScript では、たとえば次のように型を書きます（7種類のうち3つだけを抜き出した例です）。

```ts
type ServerMessage =
  | { type: "snapshot"; seq: number; notes: Note[] }
  | { type: "note.moved"; seq: number; note: Note }
  | { type: "error"; requestId: string; code: "conflict" | "invalid" | "not_found"; message: string };
```

## 5. 同時に操作したときの扱い

| 操作 | 扱い方 | 理由 |
|---|---|---|
| 移動 | あとからサーバーに届いた操作を採用する（後勝ち） | 位置は上書きされても困らず、仕組みが単純 |
| 文字の変更・削除 | 付箋ごとの `version` で確認する（楽観ロック）。送られた `version` が今の値と違えば `error`（`conflict`）を返す | ほかの人の書いた文字を、気づかないうちに上書きしないため |

移動では `version` を変えません。移動のたびに `version` が変わると、ほかの人が付箋を動かしただけで、文字の変更が `conflict` になってしまうためです。

ブラウザは `conflict` を受け取ったら、最新の内容を表示し、もう一度編集してもらいます。

最初はサーバーからの通知を受け取ってから画面を更新します。慣れてきたら、自分の操作をすぐ画面に反映し、サーバーの結果で確定または取り消す方式（楽観的更新）に進みます。

## 6. データの保存

| テーブル | 主な列 |
|---|---|
| `boards` | `id`、`name`、`created_at` |
| `notes` | `id`、`board_id`、`text`、`x`、`y`、`version`、`updated_at` |

- 最初は、Hub が操作を1つ処理するたびに DB に書き込みます。
- Hub は1つの操作を、検証、DB への書き込み、メモリ上の状態の更新、全員への通知の順に処理します。DB への書き込みに失敗したら、メモリ上の状態は変えずに、送った本人に `error` を返します。
- Hub が DB の書き込みを待っている間は、そのボードのほかの操作も待たされます。そのため、書き込みにはタイムアウト付きの `context` を使います。
- 操作が多くなったら、まとめて書き込む方式を検討します（ADR の候補）。

## 7. 画面側（TypeScript / React）の設計

- 付箋の一覧は `useReducer` で管理し、サーバーから届いたメッセージをそのまま action として reducer に渡します。reducer は入力だけで結果が決まる関数なので、Vitest でテストしやすくなります。
- WebSocket の接続・再接続・接続の状態（接続中／切断中／再接続中）は、1つのカスタムフックにまとめます。切断中は操作できないようにして、そのことを画面に表示します。
- 再接続は失敗するたびに待ち時間を少しずつ延ばしながら試します。つながったら、スナップショットで画面の状態を置き換えます。
- 付箋のドラッグ中は自分の画面だけで動かし、手を離したときに `note.move` を送ります。動かしている間ずっと送ると、通信量が増えすぎるためです。
- 付箋の文字はテキストとして表示し、HTML として解釈させません（XSS を防ぐため）。
- ボードの一覧と作成は REST なので、Phase 3 と同じく TanStack Query で扱います。

## 8. セキュリティと上限

- 接続元のサイト（Origin）を確認する
- メッセージの大きさ、付箋の文字数、1つの接続から送れる操作の回数に上限を設ける
- 入力はサーバー（Go）側で必ず検証する。画面側の検証は使いやすさのためのもの
- ログインを入れたら、WebSocket の接続時にもセッションを確認する

詳しくは OWASP の [WebSocket Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html) を参照します。

## 9. テスト

| 対象 | 方法 |
|---|---|
| Hub（Go） | 偽の接続から操作を送り、全員に配られる内容と順番を確かめる単体テスト。`go test -race` で実行する |
| WebSocket の通信（Go） | `httptest` で立てたサーバーに実際に WebSocket でつなぐ統合テスト |
| 同時編集（Go） | 複数の接続から同じ付箋を同時に変更し、`conflict` が正しく返ることを確かめる |
| reducer（TypeScript） | メッセージの並びを流し込み、最後の状態を確かめる。手元より古い `seq` のメッセージを無視できるかも確かめる |
| 手動 | ブラウザを2つ開き、同じ付箋を同時に動かしたり編集したりする |

## 10. 運用で気をつけること

- Google Cloud Run は WebSocket に対応していますが、接続はリクエストのタイムアウト（初期値5分、最大60分）で切れます。そのため、ブラウザ側の再接続は必須です（[Cloud Run の WebSocket の説明](https://docs.cloud.google.com/run/docs/triggering/websockets)）。
- サーバーを複数台にすると、ボードの状態が台ごとに分かれてしまいます。最初は1台で動かします。複数台にする場合は、台をまたいで通知を配る仕組み（Redis や PostgreSQL の LISTEN/NOTIFY など）が必要になります。
- 接続数、動いている Hub の数、送信待ちがあふれて切断した回数を記録しておくと、問題に気づきやすくなります。

## 11. 作る順番とロードマップとの関係

| 段階 | 中身 | 始められる時期 | 目安 |
|---|---|---|---|
| M1 1人用のボード | 画面だけで付箋の追加・移動・編集・削除を作る。状態は `useReducer` で持ち、サーバーは使わない | Phase 3 を終えたあと | 1〜2週 |
| M2 みんなで見えるボード | Go の WebSocket サーバーを作る。ボードは1つ、データはメモリ上に持ち、操作を全員に配る | Phase 4 を終えたあと（学習ガイド第35週の `net/http` の部分を先に読む） | 2週 |
| M3 消えないボード | ボードを複数にし、PostgreSQL に保存する。`version` による競合の確認、`seq` と再接続を入れる | Phase 5 を終えたあと | 3〜4週 |
| M4 公開 | ログインとメンバー、Origin の確認、デプロイ、監視 | Phase 6 を終えたあと | 2〜3週 |

おすすめの進め方は次のとおりです。

- ロードマップの題材（備品貸出管理）は変えずに進めます。
- M1 は Phase 3 のあと、M2 は Phase 4 のあとに、寄り道として作ります。学んだ直後に別の題材で使うと、身につきやすくなります。
- M3 と M4 はロードマップを終えてから作ります。

この進め方では、全体の期間が2〜3か月ほど延びます。ロードマップの題材をこのボードに差し替えることもできますが、学習ガイドの各週の作業をかなり読み替える必要があるため、おすすめしません。

## 12. AI の使い方

ロードマップと同じルールで進めます。

- M1 と M2 のコードは自分で書き、AI にはレビューを頼みます（Lv2）。
- M3 以降はロードマップで Lv3 まで進んでいれば、AI に実装させて自分がレビューします。

このアプリで、AI のコードを見るときに特に確かめる点は次のとおりです。

- 終了しない goroutine がないか（接続が切れたあと、Hub が終わったあと）
- 終了しかけの Hub に新しい接続が送ろうとして止まる競合がないか（Hub を一覧から消す処理を、一覧の mutex の中で行っているか）
- 送信待ちの channel があふれたときの扱いがあるか
- 1つの接続に、複数の goroutine から同時に書き込んでいないか（使うライブラリが安全かどうかも確かめる）
- Origin の確認を無効にしたままになっていないか
- 付箋の文字を HTML として表示していないか

## 13. 作り始める前に決める設計判断（ADR の候補）

| 判断 | この設計メモでの案 | ほかの選択肢 |
|---|---|---|
| WebSocket のライブラリ | coder/websocket | gorilla/websocket |
| ボードの状態の持ち方 | ボードごとの goroutine（Hub） | mutex で守った map |
| 同時に操作したときの扱い | 移動は後勝ち、文字の変更と削除は `version` で確認 | すべて後勝ち、CRDT |
| DB への書き込み | 操作ごとに書き込む | 一定時間ごとにまとめて書き込む |
| 最初の表示 | WebSocket で接続直後にスナップショットを送る | REST で取得してから WebSocket につなぐ |

それぞれ、なぜその案を選ぶか（または変えるか）を ADR に書いてから作り始めます。
